# Phase 5: Dokploy deploy (evidence record)

Run on 2026-10-27 against production, https://dev.zeikcookson.com, served by the user's Dokploy host. There is no preview app and no deploy pipeline: the owner clicks Deploy in Dokploy and runs the smoke test by hand. The user does DNS and the Cloudflare dashboard settings, Dokploy, every push and merge, the passkey, the storage bucket and the host shell. The executor makes read-only requests to public routes (the EmDash health route is public and is requested too), runs the parity tooling, reads GitHub runs with gh and writes this record. Admin state is the user's report. Secrets and the host IP are never written here; a secret that must be referred to is written REDACTED.

## Decisions applied

- Cloudflare Pages is dropped (user, 2026-10-27, D-05 to D-07 as amended): one Dokploy app is deployed straight to dev.zeikcookson.com, with no preview, the old site torn down with no rollback target, and no Pages project left to hold a stale custom domain.
- The deploy follows the EmDash Node and Docker deployment docs: the repo Dockerfile, port 4321, EMDASH_SITE_URL as a build argument and as a runtime variable per D-08, one volume at /app/data holding SQLite and uploads, and one replica.
- D-02 as amended: the wizard option is Sample content. Import an existing EmDash site is the site-transfer upload and applies no content. EmDash applies pending migrations itself on the first request after the container starts in the default auto mode, with no separate step, plus GUARD-02 and the committed-manifest gate in CI per DEPLOY-02 as amended and gate e. The EmDash docs advise keeping the manifest out of git; committing it here is the user's deliberate upgrade tripwire from plan 05-02.
- Manual deploys (user, 2026-10-27, D-15 superseded): the owner clicks Deploy in Dokploy, Auto Deploy stays off, a push to main runs ci only, and the owner runs `node scripts/smoke-test.mjs https://dev.zeikcookson.com` after each deploy. The automated pipeline from plan 05-01 (a tag-triggered deploy workflow, a deploy gate, a Dokploy API deploy script, an API key and three GitHub secrets) was dropped before it ever ran against production; plan 05-04 removes its committed code.
- One passkey (user, 2026-10-27, D-09 amended): the two-passkey requirement is dropped. The lockout risk is accepted: if the one device is lost, the way back in is the SQLite recovery procedure in PROJECT.md, which was rehearsed locally in Phase 1 and is not rehearsed in the production container.
- One replica and Dokploy's default stop-first update order are assumed and were not read from the panel (research Pitfall 9: two containers on one SQLite volume must not overlap); the panel is not changed for it.
- Agent access is OAuth to the committed .mcp.json, server emdash (user, outside Phase 5, 2026-10-27): the scoped token, the guard hook and the README agent section were removed, so this phase has no agent-token work. The only agent check is that the OAuth MCP connection still works once the proxy is on.
- The dev record starts DNS only (grey cloud) so that Let's Encrypt validated straight against Traefik and the first checks measured the Dokploy host. Plan 05-04 turns the Cloudflare proxy on with SSL/TLS Full (strict) and Always Use HTTPS off (D-16).
- EMDASH_ENCRYPTION_KEY is not set, because it encrypts plugin settings declared as secrets and the site runs no plugins.
- There is no CI image build, because the Dokploy host build is the build proof (D-01, gate d).
- Backups go to a private Cloudflare R2 bucket as the S3 destination, nightly with the container stopped. The recovery point is the raw volume copy, because EmDash's JSON backup cannot be restored (user, 2026-10-27, D-13, D-17, plan 05-05).

## Manual deploy and rollback

To deploy, merge to main and push, which runs ci only. Then open Dokploy, click Deploy on the portfolio application, wait for the deployment to show done, and run the smoke test with node scripts/smoke-test.mjs https://dev.zeikcookson.com. Auto Deploy stays off, so a push never deploys by itself.

To roll back, revert the bad commit on main, push it and click Deploy, or point the Dokploy app at an earlier branch or tag and click Deploy. Neither route has been rehearsed. A code rollback does not undo a migration that already ran (EmDash updating guide), so after a bad migration restore a volume backup, and take a backup before deploying an EmDash upgrade. Plan 05-05 sets up the nightly backup.
