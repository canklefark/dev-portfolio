# Phase 5: Dokploy deploy (evidence record)

Run on 2026-10-27 against production, https://dev.zeikcookson.com, served by the user's Dokploy host. There is no preview app; plan 05-06 adds one temporary scratch instance. The user does DNS and the Cloudflare dashboard settings, Dokploy, the GitHub secrets, every push, the merge and every tag push, the setup wizard, passkeys, the storage bucket and the host shell. The executor makes read-only requests to public routes, runs the parity tooling, reads GitHub runs with gh and writes this record. The executor never requests an _emdash URL, so admin state in this record is the user's report. Secrets and the host IP are never written here; a secret that must be referred to is written REDACTED.

## Decisions applied

- Cloudflare Pages is dropped (user, 2026-10-27, D-05 to D-07 as amended): one Dokploy app is deployed straight to dev.zeikcookson.com, with no preview, the old site torn down with no rollback target, and the hostname removed from the old project's custom domains.
- The dev record starts DNS only (grey cloud) so that Let's Encrypt validates straight against Traefik and every check in plans 05-03 and 05-04 measures the Dokploy host. Plan 05-05 turns the Cloudflare proxy on after the first tag deploy, with SSL/TLS Full (strict) (user, 2026-10-27, D-16).
- The deploy follows the EmDash Node and Docker deployment docs: the repo Dockerfile, port 4321, EMDASH_SITE_URL as a build argument and as a runtime variable per D-08, one volume at /app/data holding SQLite and uploads, and one replica.
- D-02 as amended: the wizard option is Sample content. Import an existing EmDash site is the site-transfer upload and applies no content. EmDash applies pending migrations itself on the first request after the container starts in the default auto mode, with no separate step, plus GUARD-02 and the committed-manifest gate in CI per DEPLOY-02 as amended and gate e. The EmDash docs advise keeping the manifest out of git; committing it here is the user's deliberate upgrade tripwire from plan 05-02.
- The first deploy builds emdash-migration. The merge push then runs ci only, and the first v* tag push is the first pipeline run, which sets the application's source ref to the tag (D-05, D-15 as amended).
- Deploys are tag deploys (user, 2026-10-27, D-15, amended the same day so that Dokploy builds the tag and not the tip of main). A push to main runs ci only, and a pushed v* tag runs deploy.yml. Its gate checks that the ref is a v* tag, that the tagged commit is on main and that it has a successful ci run, before dokploy-deploy.mjs sets the Dokploy source ref to the tag, deploys it and waits for done. The smoke test then runs, alert only (D-04). The tag names exactly the code that goes live, and a bad deploy is recovered by redeploying an earlier tag. Documentation-only pushes run neither ci nor deploy.
- EMDASH_ENCRYPTION_KEY is not set, because it encrypts plugin settings declared as secrets and the site runs no plugins.
- There is no CI image build, because the Dokploy host build is the build proof (D-01, gate d).
- Backups go to a private Cloudflare R2 bucket as the S3 destination, nightly with the container stopped. The recovery point is the raw volume copy, because EmDash's JSON backup cannot be restored (user, 2026-10-27, D-13, D-17, plan 05-06).
