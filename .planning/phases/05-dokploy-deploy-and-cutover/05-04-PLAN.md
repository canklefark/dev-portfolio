<objective>
Hand the deploy to a tag-triggered, CI-gated pipeline that makes Dokploy build the tag itself, and prove it with the first real tag push (user decisions 2026-10-27, D-15 as amended). A push to main runs ci only; production deploys when a v* tag is pushed, after a gate verifies that the ref is a v* tag, that the tagged commit is on main and that its latest ci run succeeded; then the deploy script sets the Dokploy application's source ref to that tag through the Dokploy API, requests the deploy and waits for done, and the smoke test runs (D-04). The tag therefore names exactly the code that goes live, and a bad deploy is recovered by redeploying an earlier tag. Documentation-only pushes get paths-ignore so they run no ci and no deploy. Then, with the record still DNS only, record the parity run, the malformed Host header check (D-10) and the response headers (D-11) at the origin, write the release procedure including what happens when a tagged commit has no ci run, and write the steps for recovering from a bad deploy.

Purpose: after this plan a release is a tag on a commit of main, the deploy builds that tag and is smoke-tested, documentation commits cost nothing, and there is no preview app and no other site to fall back on (user decision 2026-10-27), so both the release procedure and the recovery path are written down and the pipeline has worked once for real. Plan 05-05 then turns the Cloudflare proxy on (D-16).

Output: scripts/deploy-gate.mjs and the extended scripts/dokploy-deploy.mjs with their tests, the rewritten deploy.yml and the edited ci.yml, and 05-EVIDENCE.md with rows C9 to C12, the Release procedure and the Bad deploy recovery sections.
</objective>

The expectation the gate makes explicit (D-15 as amended): the ref is a v* tag, and sha, the commit it checks, is the commit Dokploy will build, because dokploy-deploy.mjs sets the Dokploy source ref to that tag before it deploys. Checks, in this order: (0) the ref, with no request: refType must be tag and refName must start with v; then two GET requests, each with headers accept application/vnd.github+json, authorization Bearer, x-github-api-version 2022-11-28 and a 15 second timeout, the second made only when the first passes:
1. /repos/{repository}/compare/{sha}...main. body.status is identical, ahead (main is ahead of sha, so sha is an ancestor of main), behind or diverged; body.ahead_by counts the commits main is ahead. On main means identical or ahead.
2. /repos/{repository}/actions/workflows/ci.yml/runs?head_sha={sha}&per_page=100. body.workflow_runs is a list of runs with id, status, conclusion, event, created_at and head_repository.full_name. A run counts only when head_repository.full_name equals repository and event is push or workflow_dispatch (a pull request or fork run never counts, T-05-24). The newest counting run by created_at (the larger id on a tie) decides: status completed and conclusion success passes.
